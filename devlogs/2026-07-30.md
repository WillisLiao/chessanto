### Principal findings

Full detail lives in `handoffs/NEXT-SESSION-ANALYSIS-CORRECTNESS.md`.
The summary judgement is that the architecture is strong and the numbers feeding it are not.

**The single highest-leverage defect is analysis depth.**
`EngineService.swift:21-27` uses movetime rather than depth, with standard at 350 milliseconds per position.
The classification thresholds distinguish a 9-point win-probability drop from an 11-point one, which is below the evaluation noise floor at that budget in sharp positions.
Movetime is also not reproducible, so re-analysis produces different classifications, different key moments, and a churning spaced-repetition queue.
Every teaching surface in the app is downstream of these numbers.

**Four correctness holes compound it.**
No book move exemption despite `deepestBookPly` already being computed by `ReportBuilder.buildOpeningFact`.
No forced-move handling, and `WinProbability.fromMate` returning a hard 0 or 100 means every move after an opponent's forced mate appears as a blunder.
`Accuracy.average` is a plain arithmetic mean where Lichess uses a volatility-weighted and harmonic combination, so the percentage is not comparable to the one users will compare it against.
`ThemeDetector.punishment` fires on any capture-first principal variation, so ordinary trades render as hanging pieces, and that false fact propagates into practice card themes, Player Brief motifs, and the takeaway generator.

**`MoveClassification.brilliant` is assigned nowhere** despite having a color, a `!!` mark, a glossary entry, and a coach headline.

**`KeyMomentSelector` does not filter to the user's side**, so the eight-slot register mixes both players while `TrainingCardFactory` filters afterward, which is why the register and the practice card count disagree.

**The flow locks the valuable surfaces behind a chore.**
Player Brief, the accuracy trend, motifs, and the review queue all need many analyzed games, and analysis is manual, one game at a time, with no batch action and no analyze-on-import.
Onboarding collects a chess.com username and then lands the user on an empty window with an "Import PGN…" button.
Player Brief is hard-gated behind chess.com confirmation, so a PGN-only user, explicitly supported by the README, can never see their progress.

**The board will read as broken to a beginner.**
`BoardView` has no drag and drop, no piece animation, no sounds, and no right-click annotation arrows.
`GameReplayViewModel.playMove` auto-queens with no picker, and `PracticeSessionViewModel.select` builds a four-character UCI that cannot match a five-character promotion `bestMoveUCI`, so a promotion practice card is probably ungradeable.
That last one needs direct reproduction before any fix, per the repository's bug-fix rule.

**The teaching level setting is cosmetic.**
`RatingRegister` injects one sentence into the LLM system prompt and changes nothing else.
Beginners and advanced players receive identical thresholds, moment counts, principal variation lengths, practice cards, and grading strictness.

**The LLM Coach is currently a liability.**
The committed screenshot shows it answering an open-ended question with three tautologies, repeating the identical answer verbatim, and promising an evaluation check it never performs.
The verifier passed it because the moves were legal and no evaluation was claimed, which exposes the structural limit: grounding proves nothing false was said, not that anything useful was said.
`CoachModelCatalog` defaults to `qwen3:4b` under 16GB, so this is the default experience.

### Recommended order

1. Analysis correctness: fixed depth, book exemption, forced and decided positions, accuracy aggregation, punishment gating.
2. Flow: batch analysis, onboarding that ends in an analyzed game, land on Review, unlock Player Brief for PGN-only users.
3. Board: drag and drop, promotion picker and the promotion practice bug, animation, sounds, annotation arrows.
4. Teaching: make the rating register do real work, add the detectors that explain real games, fix the takeaway generator, implement `brilliant`, multi-ply practice cards, a real spaced-repetition scheduler, beginner vocabulary.
5. Decide what the Coach is for.

## Priority 1 implementation: analysis correctness

### Corrections to the review document

**Already-lost positions do not flood the report with blunders.**
The review claimed `WinProbability.fromMate` returning a hard 0 or 100 meant every move after an opponent's forced mate would register a 100-point drop.
It does not.
Once the mover's win probability is pinned at 0 the drop is `max(0, 0 - 0)`, so those moves grade `.excellent`.
Probed directly against `MoveClassifier` before writing any code, and the behaviour is now pinned by `movesInAnAlreadyLostPositionDoNotGradeAsBlunders`.
The real defect in that area was narrower: forced moves were graded `.best`, inflating both accuracy and the best-move count.

**The depth-12-reports-11 symptom is not a delivery race.**
Eight depth-12 searches reported depth 11 in five of them, which looks exactly like chesskit-engine's unordered response dispatch losing the final `info` behind the terminating `bestmove` - and the first fix assumed that.
`engine-smoke` now drains everything still in flight by running a second search and consuming to its own bestmove.
The depth never improves, so the line is never emitted at all and no consumer-side wait can recover it.
The ±1 ply is inherent to Stockfish under MultiPV with multiple threads.
`BoundedSearchSession`'s grace window, `settle()`, and `BatchCollector.hasReachedDepth` were removed along with the six tests covering them.

**The first depth presets were unreachable.**
Depth 18 with a 4-second ceiling reached 18 on only 14% of a 50-position game; the rest were cut off between 14 and 17, with the ceiling binding as the norm rather than as a backstop.
Retuned to depth 12/16/20 with 5s/20s/60s ceilings, then re-measured: 41 of 50 positions at depth 16 and 9 at 15.

### What changed

- **Depth budgeting.** `AnalysisQuality` carries a depth and a movetime ceiling instead of a movetime. Do not combine both limits in one UCI `go` - Stockfish then reports one iteration fewer - so the ceiling is enforced with an explicit `stop`, which also turns a ceiling hit into usable partial lines rather than a thrown error.
- **Analysis reuse.** Decided by the preset label alone, so rows written when "standard" meant 350ms would be kept under a preset now promising a depth. The real library had a game stored as "standard" whose rank-one depths ran 8 to 17. Reuse now requires the stored depth to meet the requested depth, and the UI reports the shallowest depth actually stored.
- **`.book` and `.forced` classifications.** `deepestBookPly` was already computed and discarded, so mainline theory was being flagged as inaccuracy. Both are counted and shown but excluded from accuracy. `ClassificationContext.forGame` is the single source of truth so the phone companion cannot disagree with the Mac.
- **Punishment facts.** Fired on any capture-first PV, so ordinary trades rendered as hanging pieces and fed the practice themes, the Player Brief motifs, and the takeaway rule. Now decided by replaying the capture and asking whether the piece can be taken back, with an even-length settle for genuine exchanges and a checkmate bypass.
- **Key moments.** Filtered to the user's own side when known, so the register and the practice card count stop disagreeing.
- **Accuracy.** Replaced the arithmetic mean with Lichess's volatility-weighted plus harmonic combination, fetched from `lichess-org/lila` rather than reconstructed. Fixture game: White 94 to 90, Black 91 to 75.
- **Training grading.** Compared a 500ms search of the attempted move against the card's stored deep search; now searches one ply shallower than the card's own reference depth.

## Priority 3: the board

Implemented `handoffs/NEXT-SESSION-BOARD.md` in the order it suggested, with one deliberate reordering explained below.

### The promotion bug was real, and worse than the bootstrap described

The bootstrap predicted a practice promotion would grade `.incorrect` because a four-character UCI cannot match the engine's five-character `b7b8q`.
Reproducing it first, as the repository rule requires, showed the evaluator was already correct: given `b7b8q` it grades `.strong` with a loss of 0 and never touches the engine.
The defect was entirely upstream, in the UI, which could only ever produce a square pair.

Reproducing what that square pair actually does turned up the more serious half.
`ChessGame.replayLine(fromUCI: ["b7b8"], startingFEN: "8/1P6/8/7k/8/8/8/4K3 w - - 0 1")` returned SAN `b8` and the FEN `1P6/8/8/7k/8/8/8/4K3 b - - 0 1` - **a white pawn standing on b8**.
That illegal position was then handed to Stockfish to be scored.
So the bug was not only "the learner cannot answer correctly", it was "the grader evaluates a position that cannot exist".

`replayLine` now stops at a pawn move onto the back rank that names no promotion piece.
The alternatives are both wrong: leaving the pawn there yields the illegal position above, and assuming a queen invents a move the caller never made.
Three ChessCore tests cover it, including an underpromotion that must produce a knight rather than a queen.

### One interaction state machine instead of two

The bootstrap ordered B2 (promotion) before B1 (drag), but also warned that the two interactive boards keep independent copies of the same select-then-move logic and had already drifted.
Writing the promotion picker into both copies and then merging them would have meant writing it twice, so the shared machine landed first and promotion was written into it once.

`BoardInteraction` is a pure value type holding the selection and the pending promotion.
It takes the board's knowledge per call through a `Context` of closures, so it never holds a view model, a store, or a game, and returns a `Resolution` the caller executes.
Both `GameReplayView` and `PracticeSessionViewModel` now drive it, and `BoardInteraction.Move.uci` is the single place a promotion becomes five characters.

A click and a drop deliberately differ: clicking a square the selected piece cannot reach retargets the selection to a piece standing there, while dropping on one returns the piece and selects nothing. Retargeting on a drop would move the selection to wherever the pointer happened to land.

### The rest

- **Drag and drop** runs as a `simultaneousGesture` alongside the existing per-square buttons rather than replacing them, so tap-to-move survives as the accessible path and all 64 `square-<algebraic>` accessibility identifiers the QA scripts drive are untouched. A 4pt threshold separates a drag from an unsteady click.
- **Animation** moves the arriving piece by animating a 1-to-0 scalar the piece layer multiplies by, not the piece's `position`. Nothing about the board's geometry changes, so the surrounding column cannot reflow and resize the board - the constraint `LinesPanelView` already documents. 180ms ease-out, skipped entirely under Reduce Motion.
- **Sounds** are synthesized by `scripts/generate-sounds.py` rather than fetched, so there is no third-party licence to track alongside the GPLv3 build. A move is one dry resonant knock; a capture is the scrape of the taken piece plus a knock. `BoardSounds.isEnabled` starts **false** and is set once `GameLibrary` has read the stored preference, so nothing makes a sound before the app knows whether the user wants sound.
- **Coordinates** went from 16% of the square to 22% with an 11pt floor and a bold weight. At 16% they were the smallest text in the app, read constantly by exactly the users who most need them. They are now `accessibilityHidden` because each square's button already carries its own name.
- **Annotations do not persist, deliberately.** An annotation is a thought about the position on the board and is cleared when the board shows another one, which is what lichess and chess.com do. Persisting them needs a position-keyed table, an answer for what happens to them when a game is re-analyzed or a variation is deleted, and UI to manage the accumulated set. Right-drag comes from `RightDragCatcher`, an `NSViewRepresentable` that claims hit tests only while a right-mouse event is being routed, so left clicks pass straight through to the squares.

### A data-safety defect found while setting up QA

The live database's modification time was inside this session, and it had gained the new `v10_boardSounds` migration.

`xcodebuild test` on the app scheme launches the real app as its test host, and that host builds a `GameLibrary` - and therefore a `GameStore.defaultStore()` - during SwiftUI startup.
The existing `XCTestConfigurationFilePath` guard did not catch it.
This is pre-existing and had been harmless only because no previous session added a migration while running the tests.

Confirmed by registering a throwaway `v11_probe` migration and watching it appear in the live database after a test run.
`GameStore.isRunningUnderTests` now also treats a loaded XCTest runtime, a loaded `.xctest` bundle, and SwiftPM's `swiftpm-testing-helper` as test contexts; a `v12_probe` migration then did **not** reach the live database.
The SwiftPM arm matters separately: swift-testing package suites load neither XCTest nor a bundle, so a package test calling `defaultStore()` would have written to `~/Library/Application Support/Chessanto`.

The live database was restored from the backup taken before the probe, passes `PRAGMA integrity_check`, and holds its 15 games, 668 analysis rows, 10 training cards and 75 variations.
It retains `v10_boardSounds`, which is the schema the app applies on its next launch regardless.
Its hash is now `173a3693267582696c9ce2415d83cf6d3e158089fab9116d6fe550a5ca72c133`; the `e9947b…` recorded on 2026-07-30 predates that migration.

## Priority 2: flow (P2.1, P2.3, P2.4)

The product's most valuable surfaces were locked behind work the product never offered to do.

### P2.1 Batch analysis

`BatchAnalysisCoordinator` runs analysis over many games, one at a time, reusing the existing single-game entry point `MacCompanionManager.analyzeLocally`.
Sequential by design rather than by omission: there is one shared Stockfish and `GameAnalysisApplicationService` already serializes on it, so concurrency would queue inside the engine while making progress unreportable and cancellation vague.

The work is supplied to `start(games:analyze:)` rather than to the initializer, because the thing that actually analyzes a game lives in an environment object a `@StateObject` cannot reach when it is constructed.

A failing game is recorded and the run continues.
The entire value of a batch is that it can be left alone, which it cannot be if one unreadable PGN ends a fifty-game run - and the library is already known to contain one game that fails to parse.
The summary names the first failure rather than only counting failures.

The sidebar bottom bar gains an "Analyze N" action that appears only when unanalyzed games exist, and `BatchAnalysisBar` shows progress with a Stop button above it.
`ChessComFetchView` gained an "Analyze after import" checkbox, default on, which hands the freshly imported games straight to the coordinator - the moment the user has just said which games they care about is the right moment to offer it.
Imported games are matched back by `sourceURL` rather than by import order, since the register sorts by played date.

### P2.4 Player Brief for PGN-only users

The snapshot builder was already generic over a player name, matching `white`/`black` case-insensitively; only the gate was chess.com-specific.

`playerName` is a new nullable `userProfile` column (`v11_playerIdentity`), deliberately separate from `chessComUsername`: a PGN-only user has an identity in their own games without having an account, and the README promises to support them.
`BriefIdentity` resolves the two - a confirmed account wins, an unconfirmed username is ignored because it is only a typed guess - and ranks candidate names by how often they appear so the user's own name is normally offered first, with alphabetical tie-breaking so the list does not reorder between launches.

The dead-end "Confirm your chess.com account" panel is now a "Which player are you?" picker over the names in the register, and Settings gained a matching control so the picker's "you can change this later" is true.

### P2.3 Land on Review

`rightPaneTab` now defaults to `.report`.
The scoresheet is one click away; the report was two clicks plus knowing it existed, in an app whose purpose is game review.

The unanalyzed Report tab used to read "Analyze this game (see the Analyze button above the board)", pointing at a control instead of being one.
It is now a real primary button, disabled with the engine's own reason while the engine is still starting.
