# 2026-08-25 - Chess960 core rules and import

Branch: `feature/chess960-core`. No merge, no push.

## Handoff to the integration session - public API

Everything lives in `Packages/ChessCore` (`Chess960.swift` plus extensions
on `ChessGame`). The app never imports ChessKit for any of this.

Generating and starting a Chess960 game:

- `Chess960.backRank(index: Int) -> String` - the 8-character rank-1
  arrangement (e.g. `"RNBQKBNR"` for index 518, which is standard chess)
  for any index in `0...959`. Deterministic and seedable.
- `Chess960.backRank(seed: UInt64) -> String` - convenience wrapper
  (`seed % 960`).
- `Chess960.index(of backRank: String) -> Int?` - inverse of the above.
- `Chess960.isValidBackRank(_:) -> Bool` - validates both invariants
  (bishops on opposite colors, king strictly between rooks).
- `Chess960.startingFEN(index:useShredderFEN:) -> String` - full starting
  FEN. Defaults to Shredder-FEN castling letters (e.g. `AHah`) because
  plain `KQkq` is ambiguous in 960. There is also
  `startingFEN(seed:useShredderFEN:)`.
- `ChessGame(chess960Index index: Int)` or
  `ChessGame(startingFEN: Chess960.startingFEN(index:))` - construct a
  playable game. A genuine 960 start automatically carries
  `[SetUp "1"]`, `[FEN "..."]`, and `[Variant "Chess960"]` tags into
  `pgnString`; a non-standard non-960 FEN gets SetUp/FEN but no Variant.
- `ChessGame.isChess960` is not exposed; use
  `game.tags["Variant"] == "Chess960"` if the UI needs to know.

Playing moves:

- Castling works through the normal `playMove(from:to:)` /
  `playMove(san:)` APIs with no special-casing by callers. Two entry
  conventions are supported, matching Lichess: drop the king onto its own
  rook, or jump the king multiple files to the g/c file. A single-file
  king step to the g/c file stays a plain king move.
- `legalMoves(from:at:)` additionally offers the castled-king square and
  the rook square when castling is legal, so a UI can highlight either.
- `fen(at:)` remains authoritative. Internally ChessKit's FEN serializer
  drops Shredder rights, so ChessCore maintains correct FENs itself per
  position; callers must keep using `fen(at:)` and not reach into raw
  positions.

Persistence / GameRecord:

- Nothing about persistence needed to change. A 960 `GameRecord` looks
  exactly like a normal one; the PGN it round-trips carries the
  Variant/SetUp/FEN headers and imports cleanly via `ChessGame(pgn:)`.

## What was done

Resumed uncommitted work from the prior session (committed first as a
checkpoint), then reviewed it on its merits and fixed five real problems:

1. `CastlingRights.shredderFEN` emitted descending letter order (`HAha`)
   while `startingFEN` and every real-world FEN use ascending canonical
   order (`AHah`). Fixed to sort ascending.
2. `ChessGame.init(startingFEN:)` tagged EVERY non-standard FEN as
   `Variant "Chess960"`, mislabeling from-FEN standard mid-game imports.
   Now uses `Chess960.isChess960(startingFEN:)`.
3. Castling interception hijacked single-file king steps to the g/c file
   (e.g. plain Kf1-g1 became a castle). Now follows the Lichess
   convention: king onto own rook, or multi-file king jump only.
4. ChessKit's FEN serialization silently strips non-standard castling
   rights (`AHah` -> `-`). After any normal move this erased 960 castling
   rights everywhere that trusted `position.fen`: engine-move replay
   (`replayLine`) and both `playMove` paths lost rights after one quiet
   move, making later castling impossible mid-game. Added a shared
   `carryingCastlingRights` splice (the same trick the PGN parser already
   used) so all three paths preserve rights; regression-tested.
5. Both `playMove` castle branches recorded the move in ChessKit's tree
   as a plain king move, leaving the rook unmoved in ChessKit's internal
   board; the next rook SAN then failed to resolve (this silently broke
   139 entries of the ECO dataset replay test). Standard-game castling
   now goes through ChessKit's native `.castle` path first; the Chess960
   layer is a fallback only for positions ChessKit cannot represent.
   Also taught `replayLine` about generic 960 castle UCIs (any king start
   file jumping to g/c), not just e1g1/e8g8/king-to-rook.

New tests cover: canonical Shredder ordering after castling, the
one-step-king convention, generic 960 castle UCI replay plus a negative
(rook-to-c-file is not castling), rights survival across normal moves in
both replay and play followed by a successful castle, 960 PGN export
round-trip of headers/SAN/FENs, and no Chess960 tag on standard from-FEN
games.

Verification against real games: two real Lichess Chess960 exports are
fixtures (yoseph2013-penguingim1 Titled Arena September '25 with both
sides castling, and DrNykterstein-Vladimirovich9000 ending in Re7#); both
parse fully including castling SANs at the right plies, and the export
round-trip test re-imports the first fixture byte-for-byte on tags,
SANs, and FENs.
