## P4.1 + P4.7: register-driven teaching depth and beginner vocabulary

### The layering problem

`RatingRegister` (beginner/intermediate/advanced) lived in CoachKit and had exactly one effect anywhere in the app: one sentence injected into the LLM system prompt.
`ReportBuilder`, `KeyMomentSelector`, and `ReportText` - the code that actually decides what a report contains and how it reads - live in AnalysisKit, which has no dependency on CoachKit and must never gain one (CoachKit depends on AnalysisKit, not the reverse).
The register was defined in the wrong package for the report-building code to use it at all.

### Design consult

Given the cross-package interface question and the pedagogical judgment calls involved (exact thresholds, what "a moment with a concrete nameable consequence" should mean operationally, whether to derive a material-equivalent number from a win-probability swing), this was routed to an Opus advisor for a concrete design rather than decided ad hoc.
The advisor read the actual code (not just the backlog doc) and caught two things the backlog doc got wrong: `KeyMomentSelector`'s doc comment claims a floor of 3 key moments that the code never actually implements, and `FactAuditor` re-derives and equality-checks `BetterMoveFact.lineSANs` against `ThemeDetector.betterMove`'s output - so truncating the principal variation at detection time (the backlog doc's Q6) would have silently dropped every `BetterMoveFact` from every report, at every register, the moment this landed.

The advisor's design: move `RatingRegister` to AnalysisKit verbatim, with CoachKit keeping a `typealias` so every existing CoachKit call site keeps compiling untouched.
Store the resolved register on `GameReport` itself (not threaded through nine separate render-call sites) so a report renders consistently everywhere it appears - Report tab, Coach stage, training explanations, the phone companion payload - without each caller having to re-resolve the same profile.
Truncate the better-move line at render time in `ReportText`, never at detection time, so the audited fact stays canonical.
Default every new parameter to `.advanced`, so every one of the roughly 14 existing call sites (App layer plus both packages' test suites) stays byte-identical, provable by the pre-existing golden fixture test passing completely unmodified.
Never derive a material-equivalent number from a win-probability swing - `EvalSwingFact` carries only probabilities, and inventing a pawn-count from a sigmoid would be the first free-composed, unaudited chess claim in a codebase whose entire architecture (typed Facts -> `FactAuditor` -> fixed-template `ReportText`) exists specifically to prevent that.
Material language stays exactly where `PunishmentFact.netMaterialGainForOpponent` already licenses it.

### Implementation

Delegated to a bounded implementation worker against the advisor's frozen interfaces and numbers (key-moment cap 4/6/8 by register, better-line cap 2/4/6 plies, the exact beginner sentence templates and win-probability band thresholds, the exact `hoverLabel`/`ChessGlossary.match` signatures), with TDD and the full validation suite as completion gates.

Landed:
- `RatingRegister` in AnalysisKit with five register-driven properties (`keyMomentCap`, `betterLinePlyCap`, `usesWinPercentages`, `showsEvalLabel`, `prefersNameableConsequences`); CoachKit's `CoachPayloadBuilder.swift` reduced to a one-line `typealias`.
- `ReportBuilder.build` and `KeyMomentSelector.selectPlies` gained a defaulted `register: RatingRegister = .advanced` parameter. Beginner selection prefers moments with a punishment, missed mate, or allowed mate over a bare eval swing when the cap forces a choice, but this is a sort preference, not a hard filter - a beginner game with no consequence-bearing candidates at all still gets a non-empty selection.
- `ReportText.evalSwingSentence` and `betterMoveSentence` branch on `report.register`. Beginner prose: `"27... f6 makes things much worse for Black: White is winning now."` instead of `"drops Black's winning chances from 55% to 12%."` No percentage sign, no eval-label numeral, anywhere in beginner output.
- `GameReplayViewModel.buildReport()` now resolves the register from the stored user profile's rating band (reusing the existing `userRatingInThisGame` computed property, the same one already used for the Coach payload) and threads it into `ReportBuilder.build`.
- `EvalGraphView`'s hover readout said `"Ply 27"` for every user at every register - nobody counts plies. Extracted into a testable pure `hoverLabel(ply:winPercentForWhite:)` and fixed to `"14... 63% for White"`, matching `ReportText.moveNumberLabel`'s own convention. This is a plain bug fix, not register-gated.
- `GameReportView` and `GameReplayView` each had their own hand-rolled, independently drifted `momentSummary` private function - one said "Drops winning chances", the other said "Winning chances changed" and phrased punishments differently ("is the reply to watch" vs. the canonical "This left it where it could be taken"). Both deleted; both views now call `ReportText.momentSummary(_:report:includingMoveLabel:)` directly. This was the actual root cause of the Replay pane and the Report tab disagreeing about the same moment's wording.
- `ChessGlossary` gained `match(in:) -> (term: String, gloss: String)?`, and beginner-register key-moment rows in `GameReportView` show one footnote line when a known term (en prise, hanging, O-O, O-O-O, forced mate) appears in the rendered summary. Non-interactive by design this session - a tappable/popover version needs a link scheme and new colour rules the advisor explicitly recommended deferring until the plain footnote has proven it lands.
- `PracticeContentView`'s `"Engine loss: 140 centipawns."` became `"About 1.4 pawns worse than the best move."`, register-independent since jargon-free wording helps every level.

### Verification

Independently re-ran every validation command myself rather than trusting the worker's report, after the harness flagged a batch of stale SourceKit diagnostics ("No such module AnalysisKit", "Extra argument register") across nearly every touched file simultaneously - the pattern of many unrelated modules failing to resolve at once is the signature of a stale editor index, not a real compile failure, and this was confirmed: `xcodebuild build` succeeded, `swift test` inside AnalysisKit passed 90/6, and the full app suite passed 170 tests across 34 suites (up from 159/32) when re-run from a clean shell.
The stale index traced to the worker discovering mid-task that `Chessanto.xcodeproj` is gitignored and generated from `project.yml` via `xcodegen generate` - it regenerated the project to add the two new App test files to the build target, which is the project's own established mechanism, not a hand-edit of a tracked file, but left the editor's index briefly out of sync with the regenerated project on disk.

Read the diff directly (not just the worker's summary) for `ReportText.swift`, `GameReportView.swift`'s glossary-footnote insertion, `EvalGraphView.swift`, `PracticeContentView.swift`, `GameReplayView.swift`, and `ChessGlossary.swift`, and read the full rendered beginner golden fixture to judge the actual prose quality rather than trusting that the tests merely passed:

- 27. Rc8 makes things worse for White: the position is level now. Better was Rd6 (Rd6 f6).
- 27... f6 makes things much worse for Black: White is winning now. Better was Qe4+ (Qe4+ Ka2).

`PortableReportAssembler`, `DashboardView`, `PlayerBriefView`, and `MacGameAnalysisBackend` still build their reports at the `.advanced` default regardless of the actual viewer's register - wiring those was explicitly cut from this session's scope by the advisor's design to keep the diff reviewable, and is a small follow-up whenever someone notices the mismatch.
`P4.2` through `P4.6` and `P4.8` (new detectors, takeaways, `brilliant`, multi-ply practice, spaced repetition, the LLM Coach's purpose) remain entirely unstarted; they are the harder, higher-risk remainder of "teaching depth" and were explicitly out of scope for this session.
